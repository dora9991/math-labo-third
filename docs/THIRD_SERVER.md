# 数学ラボ3 — サーバー版（チート対策）の手順と、守れる範囲

## 何を守るか
| 守るもの | 仕組み |
|---|---|
| **ガチャの抽選・チケット・所持キャラ・限界突破** | 状態は `third_player_state` に**サーバー(Edge Function `third-api`)だけ**が書く。ブラウザの保存を書き換えても変わらない。抽選もサーバーが暗号品質の乱数で行う |
| **経験値・コイン・バトルのご褒美** | バトルで解いた問題の記録(seed＋答え)をサーバーへ送り、**サーバーが seed から問題を作り直して採点**。「正解した/勝った」という自己申告は使わない |
| 二重取り・使い回し | 申請ごとの一意ID、解答(seed)の使用済み管理、申請間隔、同時送信の排他(楽観ロック) |
| 周回稼ぎ | チケットは各小単元の**初回クリアのみ**。2回目以降は経験値30%・コイン少、1日10回まで |
| 速すぎる解答 | 1.2秒未満の解答は正解に数えない／解答時間の合計が経過時間を超える申請は拒否 |

## 守れない/弱いところ（正直な限界）
- **答えそのものはブラウザのプログラム内にある**。本気で解析する人は、問題を作る関数を自分で動かして正しい答えを送れる。ただし得られるのは「小単元ごとの初回チケット1枚＋周回上限つきの少量報酬」まで（無限には増えない）。
- **メダル（はいち・れんしゅう）と、バトルの解放はまだブラウザ側**。書き換えるとバトルの入口は開くが、報酬は「サーバーが採点した正解数」が必要なので、学習せずにチケットは得られない。メダルのサーバー化は次の課題。
- 端末の時計は、サーバー時刻との差を補正して送る。

## 動作モード
- **サーバーモード**：`.env.local`（と本番ビルド環境）に `VITE_THIRD_SERVER=1`。ログイン中の生徒だけが使える。**これがチート対策版**。
- **ローカルモード（既定・開発用）**：同じ処理をブラウザ内で動かす。保存は localStorage＝書き換え可能。画面に「開発用のローカルモード」と出る。コンソールから `__thirdDev.giveTickets(20)` でチケット付与して試せる。

## デプロイ手順（1回だけ・kazuの操作）
1. `docs/supabase_third_setup.sql` を実行済みであること（済）。
2. 1ファイルにまとめる：
   ```bash
   npm run build:third-api      # → supabase/functions/third-api/bundle/index.ts（約1.3MB）
   ```
3. Supabase ダッシュボード → **Edge Functions → Deploy a new function**（名前は `third-api`）→ `bundle/index.ts` の中身を貼り付けて Deploy。
   - 「Verify JWT」は**ON のまま**（ログインしている生徒だけが呼べる）。
   - 貼り付けが重い/失敗する場合は Supabase CLI で `supabase functions deploy third-api`（要 `supabase login`）。
4. `.env.local` に `VITE_THIRD_SERVER=1` を足し、本番のビルド環境にも同じ値を設定して再ビルド。
5. **問題データや生成ロジックを変えたら**、`npm run build:third-api` でサーバーを作り直して再デプロイし、クライアントも再ビルド（版のずれたクライアントは「アプリが古いよ」と案内して拒否される）。

## テスト
`npm run test:third-api`（サーバー側ロジック27項目：ガチャの確率・天井・凸、未所持キャラの編成拒否、偽の申請/リプレイ/使い回し/速すぎ/時間矛盾/版ずれ/同時送信の拒否など）

## 学習ログ（生徒の記録をサーバーに残す）— 2026-09-25
**何が残るか**（すべてサーバーの時計・サーバーの採点。生徒のブラウザは書き込めない）
| 記録 | 表 | 中身 |
|---|---|---|
| 解答の中身 | `third_answer_log` | 1問ごとに、問題文・正解・生徒の答え・○×・誤答タイプ・かかった時間・難易度・単元・モード(バトル/れんしゅう/はいち確認)・バトルの結果(勝ち/負け/途中でやめた)。**サーバーが seed から問題を作り直して書く**ので、生徒が送れるのは「どの問題に何と答えたか」だけ。同じ問題(seed)は二重に入らない |
| その日に解いた問題数 | `third_daily` | 生徒×日(日本時間)：解いた問題数・正解数・解答時間・モード別の数・メダル数・ログイン回数・滞在時間・はじめ/おわりの時刻 |
| ログイン時間 | `third_sessions` ＋ `third_login_log` | ログイン(タブを開いた)ごとの開始時刻・最後に動いた時刻・滞在時間。1分おきの `ping`（画面が見えている間だけ。放置は1回90秒まで） |
| メダル | `third_medals` ＋ `third_player_state` | 取った日時(れんしゅう／はいち)。現在のメダルは state から導出 |
| 解答の記録（○×だけ） | `third_attempts` | 従来どおり。サーバーが検証した解答（報酬・メダルの根拠） |

**取りこぼさない仕組み**
- れんしゅう／はいち：従来どおりサーバーが採点＋今回から解答の中身も記録。
- バトル：勝った戦いは報酬の申請(claim)で記録。**負けた・途中でやめた・お試し・章ボスの解答は `report` で送る**。送る前に端末(`ml3_battle_log_queue_v1`)へ一時保存し、通信が切れても次に開いた時に送り直す。
- ログイン時間：アプリを開いた時と、その後1分おきに `ping`（`src/third/sessionPing.js`）。

**先生が見る画面**：管理モード → ラボ3の分析 → 「🗂 学習ログ」。生徒×日付の表（その日に解いた問題数）→ 名前をタップで、日ごとの記録・ログイン履歴・メダルを取った日・解答の中身（まちがいだけの絞り込みあり）。

**限界（正直に）**：ログは「生徒がその問題にそう答えた」記録で、報酬・メダルの根拠には使わない（それは従来のサーバー採点）。`report` は seed を自分で作って送れば、自分の「解いた問題数」を水増しできる（報酬・メダルは増えない）。授業での利用が前提なので、まずは許容している。

**有効にする手順（kazuの操作・順番どおり）**
1. Supabase の SQL Editor で `docs/supabase_third_setup.sql`（⑥まで）→ `docs/supabase_third_logging_2026-09-25.sql` を実行（何度実行しても安全）。
2. `npm run build:third-api` → `third-api` を再デプロイ（`npm run release` でも可。`bundle/index.ts` を貼る場合も同じ）。
3. `npm run deploy`（クライアント。会話・バトル報告・ping が入る）。
※ 1と2が済むまでは、記録の追加は静かに何もしない（ゲームには影響しない）。`admin_daily`／`admin_student_log` は表が無いと「学習ログの表がまだ作られていません」と表示する。
**テスト**：`npm run test:third-logging`（30項目：解答の中身・二重記録の防止・日跨ぎ・メダル・負けの記録・偽の報告・ping・DB障害時に止まらない）。
